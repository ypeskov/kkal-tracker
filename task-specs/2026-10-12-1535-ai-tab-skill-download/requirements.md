# Settings → AI: download the food logging skill as a ready-to-install .zip

## Overview
Today a user who wants an AI agent (Claude) to log food has to take the skill from the repository, create an API key
in Settings → API Keys, and put the key into an `api_key` file by hand. Most users can't do that, and in claude.ai
there is no way to edit a file inside an uploaded skill.

The new **AI** tab in Settings has one button that downloads the `kkal-tracker-food-log` skill as a `.zip` that is
ready to upload to Claude. The server creates a new API key for the user right before the download and puts it into the
zip. The skill is pointed at this server's public URL (`APP_URL`). On the development server the zip contains the
`-dev` variant of the skill (dev name, description and banner), so the dev and prod skills can be installed side by side.

Business value: installing food logging by voice/chat becomes a one-click step, with no copying of secrets and no
access to the repository.

## Current State
- **Skill sources** (`skills/`):
  - `kkal-tracker-food-log/SKILL.md`: frontmatter `name`, `description` (lines 1–4), the title
    `# Kkal Tracker: food diary logging`, the line ``- Base URL: `https://kcal.peskov.info` ``. The "API basics" section
    tells the agent that the key comes from `KKAL_API_KEY`, the `api_key` file next to SKILL.md, or the constant, and on a
    missing key to "ask the user to create one in Kkal Tracker (Settings → API Keys) and save it to the `api_key` file".
  - `kkal-tracker-food-log/scripts/kkal_client.py`: `DEFAULT_BASE_URL = "https://kcal.peskov.info"`,
    `API_KEY = "XXXXXXXXX"` (placeholder). `load_api_key()` reads `KKAL_API_KEY`, then `<skill dir>/api_key` (stripped),
    then the constant. `KKAL_BASE_URL` overrides the base URL.
  - `kkal-tracker-food-log-dev/`: generated by `skills/sync_dev_skill.py [URL]` (Python). The transformation: frontmatter
    line 2 → `name: kkal-tracker-food-log-dev`, line 3 → `description: ` + `DEV_DESCRIPTION`; the title gets ` (DEV)`
    plus `DEV_BANNER` after it; the Base URL line and `DEFAULT_BASE_URL` → the dev URL (default
    `https://dev-kcal.peskov.info`). Each replacement must match exactly once, otherwise the script fails.
  - `skills/*/api_key` is git-ignored. **Real key files exist in the working tree on the dev VM** (both skill folders).
  - Referenced in `README.md` ("Agent skills", `python3 skills/sync_dev_skill.py`) and `docs/architecture.md`.
- **Build / embedding**: `web/embed.go` embeds `web/dist` (`//go:embed dist`). Nothing embeds `skills/`. The
  `Dockerfile` builder stage runs `COPY . .`, so `skills/` reaches the build. **`.dockerignore` does not exclude
  `skills/*/api_key`**, and `deploy.sh` builds the production image from the dev VM's working tree (after
  `git checkout master`, git-ignored files stay). Air (`.air.toml`) watches only `go, tsx, ts, html, css, js, json`, so
  changes to `SKILL.md` / `kkal_client.py` don't trigger a rebuild.
- **Config** (`internal/config/config.go`): `Environment` (`development`|`production`, default production,
  `IsDevelopment()`), `AppURL` (default `http://localhost:8080`). The dev VM's `.env` has `ENVIRONMENT=development` and
  `APP_URL=https://dev-kcal.peskov.info`. The production image presets `ENVIRONMENT=production`, and the prod ConfigMap sets `APP_URL`.
- **API keys**: `services/apikey.Service.CreateKey(userID, name, expiryDays) (*models.APIKey, rawKey, error)` returns
  the raw 64-hex key once. It stores a SHA-256 hash and an 8-character prefix, and logs only the prefix. The handler
  (`handlers/apikey`) is under `/api/api-keys` with JWT auth and no rate limit. Key names: 1–100 characters.
- **Routes** (`internal/server/server.go`): groups under `/api`, each with `authMiddleware.RequireAuth`. Per-IP limiters
  come from `newRateLimiter` (`security.go`). In production the load balancer hides client IPs, so a per-IP limit is shared by all users.
- **Download pattern** (Excel export): `handlers/export` sets `Content-Type` + `Content-Disposition: attachment` and
  returns `c.Blob`. On the frontend, `web/src/api/export.ts` uses `fetch` with a Bearer token from sessionStorage, then
  `response.blob()` and `downloadBlob(blob, filename)` (an object URL plus a temporary `<a download>`). This is CSP-compatible and already in production.
- **Settings page** (`web/src/pages/Settings.tsx`): `TabNavigation` with tabs `export` (Download icon) and `apiKeys`
  (Key icon). State is a `useState<'export' | 'apiKeys'>` union. Tab components are in `web/src/components/settings/`.
  The API Keys tab lists keys with the `['apiKeys']` TanStack Query key. Locale keys are `settings.export.*` and `settings.apiKeys.*`.
- **Smoke test** (`internal/server/smoke_test.go`): a fully wired server covering register → activate → login → calories → weight → export.

## Requirements

### Backend
1. **Endpoint** `POST /api/skills/food-log/download` with JWT auth (`RequireAuth`) and no request body. It uses POST
   because it creates a key.
   - 200 response: `Content-Type: application/zip`,
     `Content-Disposition: attachment; filename="<skill-name>.zip"`, `Cache-Control: no-store`, and the zip as the body.
   - Without or with an invalid JWT: 401, and no key is created.
   - On any internal failure: 500 with the generic message `Failed to prepare the skill`. The error is logged with
     `user_id`, and its text never reaches the client. If the key was already created and the zip can't be produced,
     the key is deleted (best effort, failures logged), so a failed download leaves no usable orphan key.
   - Rate limit: see Q-D3.
2. **Skill variant**:
   - `cfg.IsDevelopment()` gives the dev variant (D3): the same transformation the current `sync_dev_skill.py` does
     (name `kkal-tracker-food-log-dev`, the DEV description, ` (DEV)` in the title plus the DEV banner).
   - Otherwise the production variant (name `kkal-tracker-food-log`, text unchanged apart from the base URL).
   - In both variants the base URL is `APP_URL` with any trailing `/` removed. It replaces the URL in the SKILL.md
     `- Base URL:` line and in `DEFAULT_BASE_URL` of `kkal_client.py`.
3. **Zip layout** (accepted by the user, D6): exactly one top-level folder named after the skill
   (`kkal-tracker-food-log/` or `kkal-tracker-food-log-dev/`) containing exactly these files:
   - `SKILL.md` (transformed)
   - `scripts/kkal_client.py` (transformed; `API_KEY = "XXXXXXXXX"` stays the placeholder)
   - `api_key`: the new raw key plus a trailing `\n`. The client reads this file unchanged.

   No other files: no `api_key` from the build host, no `sync_dev_skill.py`, no Go files.
4. **Key**:
   - Created through the existing `apikey` service for the authenticated user.
   - Name: `Claude skill YYYY-MM-DD HH:MM UTC` (the server's time in UTC).
   - Expiry: none (D2).
   - Earlier keys, including those from earlier skill downloads, stay as they are: no automatic revocation and no
     migration (D1).
   - The raw key is never logged. It appears only in the zip body: not in log lines, error messages or headers.
5. **Embedding**: the two source files of the production skill are embedded into the binary with `go:embed`. List them
   explicitly; a whole-directory embed would pick up the git-ignored `api_key`. The skill files must not be read from
   disk at runtime. The production image is distroless with only the binary and migrations.
6. **Single source of the transformation** (D4): the dev transformation (DEV description, banner, replacements with
   exactly-once checks) moves to Go and lives in one place.
   - One Go package is used both by the download service and by a small generator command that writes
     `skills/kkal-tracker-food-log-dev/`.
   - The generator accepts an optional URL like the script does, never touches the dev `api_key` file and keeps the
     repo copy with the placeholder.
   - `skills/sync_dev_skill.py` is deleted. Every reference to it is updated: `README.md:244`,
     `docs/architecture.md:38`, and any others (grep the repo, excluding `task-specs/`).
   - A test fails when the committed `skills/kkal-tracker-food-log-dev/` differs from the generator output for
     `https://dev-kcal.peskov.info`, which catches a forgotten regeneration.
7. **Skill frontmatter**: in both variants, `name` equals the zip folder name and is a valid skill name (lowercase
   letters, digits, hyphens; at most 64 characters). A unit test checks this. The production `description` stays
   unchanged (D5); no length requirement applies. See Known risks.
8. **Skill text** (D7): in SKILL.md "API basics" (and the `kkal_client.py` "not configured" message and the
   configuration comment), name **Settings → AI → download the skill** as the way to get a configured skill. Creating a
   key in Settings → API Keys and saving it to `api_key` stays as the manual alternative. Regenerate the dev copy.
9. **Build hygiene**:
   - Add `skills/*/api_key` to `.dockerignore`.
   - Make Air rebuild on changes to the two embedded skill files (`include_file` or equivalent; check the Air docs).

### Frontend
1. A new third tab **AI** in Settings (after API Keys):
   - Label `t('settings.ai.tab')`, a `lucide-react` icon (e.g. `Bot` or `Sparkles`).
   - The Settings tab union type gets `'ai'`.
   - The default tab stays Export.
2. Component `web/src/components/settings/AiTab.tsx`, a card in the standard layout from the `frontend-style` skill, containing:
   - Title and a short explanation of the skill: tell Claude what you ate, by text or voice, and it records it in the
     food diary, matching your ingredient list.
   - The **Download skill** button (primary style). It is disabled while the request runs and shows a "Preparing…" label.
   - A note that each download creates a new API key, and that keys from earlier downloads stay active and can be
     deleted in Settings → API Keys (D1).
   - Install steps for Claude (claude.ai), as accepted by the user (D6):
     1. In Claude: Settings → Capabilities, enable code execution and allow network access to the tracker's domain
        (shown from `window.location.host`).
     2. Settings → Capabilities → Skills → Upload skill → choose the downloaded zip.
     3. In a chat, tell Claude what you ate.

     Plus one line for Claude Code: unzip into `~/.claude/skills/`.
   - A warning styled like the existing amber warning in the API Keys modal: the zip contains a secret key that gives
     full read and write access to your diary. Do not share it. If it leaks, delete the key in Settings → API Keys and
     download the skill again.
3. API client: a new `web/src/api/skills.ts` (one file per backend domain). `downloadFoodLogSkill()` does a POST with the
   Bearer token and returns `{blob, filename}`. The filename comes from `Content-Disposition`, with the fallback
   `kkal-tracker-food-log.zip`. On a non-OK response it throws an error with a fixed message. Server text is not shown
   to the user.
4. On success:
   - Save the blob with the existing `downloadBlob` approach (an object URL and an `<a download>`, revoked afterwards;
     reuse rather than copy if practical).
   - Show `NotificationPopup` success: "Skill downloaded. A new API key was created."
   - Invalidate the `['apiKeys']` query so the new key is visible on the API Keys tab.
5. On error: `NotificationPopup` error with a localized generic message. On 429, a localized "too many downloads, try
   again in a minute" message, if a rate limit is added (Q-D3).
6. All strings through `t()` under `settings.ai.*` in all 4 locales (`en_US`, `uk_UA`, `ru_UA`, `bg_BG`). Tailwind only.
   No inline scripts. CSP stays unchanged.

## Known risks
- **Description length.** The Agent Skills format is documented with a 1024-character limit for `description`. By a
  manual count the production description is about 1150 characters; the dev description (about 630) is within the
  limit. The user chose to keep it unchanged (D5). If the claude.ai upload rejects the production zip, the description
  has to be shortened in a follow-up task. The integration check "the zip uploads to claude.ai" will show it.

## Open Questions

### For the developers (decide during implementation, record in `status.md`)
- **Q-D1**: package layout.
  - `go:embed` can't reach `..`, so the embed must live under `skills/` (e.g. `skills/embed.go`, package `skills`,
    like `web/embed.go`) or the files must move.
  - The transformation package goes in `internal/` (e.g. `internal/skill`), the service in `services/skill`, the handler
    in `handlers/skill`.
  - The generator command goes in `cmd/` (e.g. `cmd/skillgen`).
- **Q-D2**: key cleanup on failure. The order is render → create key → zip → respond. If the key is created and zipping
  fails, delete it. Once the response is being written, a broken connection can't be detected reliably; that's accepted.
- **Q-D3**: rate limit. Key creation is cheap, but one click creates one key. Recommended: a per-user limiter (identifier
  = `user_id`, e.g. a burst of 5, then 1 per minute) rather than per IP, because the prod load balancer hides client IPs.
  The frontend also disables the button while pending. Alternatively, no limit, consistent with `POST /api/api-keys`.
- **Q-D4**: Air `include_file` vs adding `md`/`py` to `include_ext`. The latter would rebuild on every doc edit.

### Out of scope
- An AI-analysis settings section on the AI tab: there are no such settings, since the provider is chosen on the AI
  Insights page.
- Showing or revoking skill keys on the AI tab: the API Keys tab handles that.
- Substituting the host in the production description text (`kcal.peskov.info`) for other deployments. Only the
  base URL is substituted.
